# 决策记录

对**难以反悔**的选择做简短记录。每条包含：决定、理由、以及在什么条件下会重新考虑。

**语言**：[中文](decisions.zh-CN.md) · [English](decisions.en.md)

---

## D-1 —— 导入工具放在注册库仓库之外

**决定。** 编辑器前端开发在 `UnityToolImport/`，一个带独立本地 git 历史的兄弟目录，而不是放在
`DevCatToolRegistry` 里。

**理由。**

- 注册库的历史应该读作「**发布了什么**」的记录，而不是一个应用的提交日志。混在一起两者都更难审计。
- 用 UPM / Git URL 引入注册库的使用者**不应该**下载到前端的源码；反过来，前端的开发者也不该被迫
  下载整个 payload 注册库。
- 二者发布节奏不同：发布一个工具是罕见且刻意的动作；前端则在持续迭代。
- 两侧的边界是一份**数据契约**（`index.yaml`、`tool.yaml`、JSON Schema），所以这个拆分在耦合上
  几乎没有成本——任一侧都可以在契约不变的前提下重写。

**何时重新考虑。** 如果契约变动频繁到两仓库之间的版本错位成为主要 bug 来源；那时「一个仓库装两个
UPM 包」会更简单。

**状态。** 按选择**尚未推送**到远程。若要发布，建议形态是一个 UPM 包
（`com.devcat.devcattoolregistry.importtool`）。

## D-2 —— 导入器是编辑器工具，不是 UPM 包管理器

**决定。** 工具由前端导入，而不是通过声明 UPM 依赖。

**理由。**

- UPM 解析的是**包**，不是**编辑器工具**：单个脚本、一个菜单项、一包资源都不是天然的包，强行
  一工具一包太重。
- UPM 无法表达「安装我挑的这三个工具并写下回执」；它只按依赖图装它要装的东西。
- 注册库必须支持非 UPM 的 payload（`.unitypackage`、`.zip`、`.tgz`、资源包、单个 `dll`）。
- 回执与带引用计数的卸载，是 UPM 不提供的需求。

**仍然支持。** 整个注册库本身是一个合法的 UPM 包，而 `artifact.type: external` 的条目可以指向真实
的 UPM 包，所以 UPM 在合适的场景仍然可用。

## D-3 —— payload 是封存归档，绝不是散装文件

**决定。** 只能导入归档或单文件制品（`archive` / `package` / `file` 三种类型），散装 `.cs` 会被
`tools/validate_registry.py` 拒绝。

**理由。** 散装文件导入无法做哈希校验、会在使用者的工程里留下未受追踪的资源，并且使精确卸载不可能。
归档是原子的、可校验的、可移除的。

**代价。** 更新一个工具意味着重新导出制品而不是就地改文件，而且注册库要存 Git 无法有意义 diff 的
二进制。

**何时重新考虑。** 如果 Unity 提供了某种一等公民的、对回执友好的方式，可以从远程注册库导入单个
源文件。

## D-4 —— 一份元信息只描述一个版本

**决定。** `tool.yaml` 描述**一个**已发布版本。多版本元信息（`versions[]`）保留给未来的
`formatVersion`，当前会被拒绝。

**理由。** 在这个规模上，简单比版本历史更值钱：解析器只会落到注册库提供的那一个版本，所以没有
「可选」的余地。完整的历史元信息会引入一个没有消费者的求解维度。

**何时重新考虑。** 当某个工具需要同时支持「给 Unity 2019 的版本」和「给 Unity 2021 的版本」，
也就是一个制品无法服务所有受支持的宿主时。

## D-5 —— 制品不可变；要改就出新版本

**决定。** 制品一旦提交，其字节永不改变。

**理由。** 回执、缓存与 `sha256` 校验全部以内容为键。改写已发布的字节会静默地让所有引用过它的回执
失效，从而摧毁卸载的精确性。**这也是版本指针能成立的前提**：回滚目标是摘要，摘要必须可信。

**强制方式。** `tools/validate_registry.py` 每次运行都重算 `sha256`，所以改动过的制品会让 CI 失败，
除非同时更新元信息——而那个信号应该被读作「该升版本号了」。

## D-6 —— 核心不认识任何引擎；适配器注册格式

**决定。** `packages/utool-core` 不含任何引擎名分支。引擎通过**容器注册表**贡献格式，通过三态的
`meetsRequirement` 贡献需求比较。

**理由。** 一个把某个引擎写死的注册库会**压制最值得拥有的那类工具**——跨引擎工具。一个 C# 库若在
Unity 和 Godot 都能用，它必须能一次说清楚，而不是被复制两份或被逼着选边。

**代价。** 适配器必须对**自己不认识的键返回 `undefined`** 而不是 `false`；写成 `false` 会在新增
需求键时静默阻断安装，反而制造出这个拆分本想避免的耦合。

**证据。** 用只装核心的容器注册表去校验真实 unitypackage 会以
`E-ARTIFACT-FORMAT-UNSUPPORTED` 失败；而 `packages/utool-core/src/` 中 `unitypackage` 仅出现在注释
里。两条都有测试或代码可直接核对。

---

## D-7 —— 回执记录文件**实际所在**的路径

**决定。** 容器处理器上报的是**项目相对**的落盘路径，不是归档内的路径。路径解析由核心的写入上下
文持有，处理器不得自行决定。

**理由。** 这是被一个真实缺陷逼出来的：归档处理器一度上报归档内路径，于是带 `contentRoot` 的
Godot payload 在回执里写的是 `plugin.cfg`，而文件在 `addons/core_utils/plugin.cfg`。**卸载会查错
位置并留下残留**，而所有单元测试都是绿的——因为它们测的是归档读取器，不是回执。

**强制方式。** 安装测试对**真实**注册库制品断言：回执里的每个路径都必须在磁盘上存在。
